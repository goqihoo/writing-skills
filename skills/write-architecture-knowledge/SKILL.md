# Write Arch Knowledge

Own reusable Architecture Knowledge not tied to one company or project commitment, from a single detailed document to a coherent knowledge system organized by its subjects and reader questions.

## Workflow

1. Read `../../methods/architecture-reasoning.md`, `../../methods/architecture-documents.md`, and `references/architecture-knowledge-method.md`.
2. Establish the requested subject, reader task, scope and mode: organize a knowledge system, write one document, revise, or review. Read the target, sources, navigation and representative siblings.
3. Read `references/knowledge-system.md` for system organization, file placement, creation or migration. Inventory actual files and responsibilities before changing topology. Preserve a requested or established healthy structure; default to objects, topics and reader questions.
4. Read `../../methods/architecture-templates/templates.yaml`. Select the template by document responsibility, not merely topic keywords. Use the four primary object-design templates according to the responsibility rules in the Architecture Documents Method. Keep topics and navigation scoped to their actual questions; existing specialist resources do not require extra artifacts. Read each selected asset before drafting; create only the artifacts justified by the request.
5. Establish the Architecture Object or recurring problem, Scope, assumptions, relevant domains/viewpoints, and evidence. Separate sourced facts, deductions, examples and project commitments.
6. Read `../../methods/prose-quality.md` and apply **Plan section questions before drafting** in the Architecture Documents Method. Build a concrete reference model with contract realization, state relationships and mechanisms, a worked behavior or change-impact example, failure/counterexample, variants and validation. Apply the usable-design checks in the Architecture Documents Method while keeping choices reusable. Use the selected template's section responsibilities and explanatory prompts; apply `../../methods/prose-quality.md` when choosing prose, figures and tables. Apply the reading-path guidance without replacing a detailed architecture with a generic essay.
7. Read `../../methods/visual-production.md` when the selected template requires visuals, the user requests them, or they materially clarify relationships; apply the selected template branch’s required-view audit before removing any figure slot; apply the complete argument edit and source recheck in `../../methods/prose-quality.md` before final expression review. Keep working checks separate from reader-facing conclusions. Honor explicit output formats.
8. Maintain authorized parent/child, dependency and source links. Verify the architecture-document reader checks, cross-document scenario check and knowledge-system completion conditions. Remove unfilled scaffold text and preserve evidence gaps honestly.

## Boundaries

- Keep reference models, options and project extraction reusable; let `$Write Tech Arch` own company Technical Architecture and concrete Project delivery architecture.
- Let `$Write Tech Doc` own stable System and Subsystem Architecture, Module Design and Component Architecture under company authority.
- Organize the requested architecture knowledge set internally; use `$Structure Docs` only for a separately requested general documentation migration, without requiring another invocation.

## Completion

For architecture artifacts, complete the design-argument review in `../../methods/architecture-documents.md`; verify the relevant design elements in the delivered prose, not only in working notes.

Complete when the requested document or knowledge set has the right templates, explicit boundaries, intelligible structure and mechanisms, applicable tradeoffs, evidence and validation limits, and coherent navigation where a set exists. Verify that readers can move from an overview to the relevant design and mechanism explanations without conflicting ownership, duplicate authority, broken local links or unintended project commitments.
