# Structure Product Docs

Give product knowledge stable homes while preserving lifecycle as a view over the files rather than a competing directory system.

## Workflow

1. Apply `$reason-product`, `$assess-product-lifecycle`, `$structure-docs`, and `$write-doc`.
2. Classify the request as a proposal, audit, scaffold, or approved migration. Obtain confirmation before moving, renaming, merging, deleting, or overwriting existing material.
3. Read repository instructions, the product and repository root maps, the Product Assessment, the Product Lifecycle Assessment, and representative adjacent product or project structures.
4. Require an `Accept` Product Assessment. Require a current lifecycle assessment for evidence-based materialization; when it is absent, return a ready-to-type explicit invocation for `$assess-product-lifecycle $reason-product $write-doc` and stop before scaffolding.
5. Read `references/product-structure-model.md`, `../write-product-doc/references/product-document-types.md`, and `assets/product-inventory-template.md`.
6. Inventory every existing and requested material by reader question, change authority, validity, content class, product document type, state, primary home, and structural issue.
7. Start from the Seven-directory core. Add Product-type extensions only when the accepted product model and current navigation need support them. Keep collections flat until an upgrade trigger is present.
8. Assign `Existing`, `Create now`, `Planned`, or `Unresolved`. A core directory may be created by an explicit scaffold request; give it a responsibility README when `$write-product-doc` is also invoked.
9. Define the root README and lifecycle-map contracts. Let `$write-product-doc` own their prose and links. Leave planned content unlinked.
10. Present or apply `assets/product-structure-plan-template.md`. If document bodies are requested without `$write-product-doc` or a standard artifact skill, return the complete explicit invocation and leave the bodies ungenerated.
11. Apply approved migrations as one change, updating navigation, links, assets, and external bindings named by the plan.
12. Verify one primary home per material, seven coherent core responsibilities, evidence-backed extensions, valid links, honest states, and no copied technical authority.

## Boundaries

- Own inventory, topology, core scaffolding, extensions, materialization, README and lifecycle-map requirements, navigation, and approved migration.
- Let `$reason-product` own product admission, hierarchy, and ownership.
- Let `$assess-product-lifecycle` own decision readiness and artifact coverage.
- Let `$write-product-doc` and standard artifact skills own document bodies.
- Let `$structure-docs` own repository-wide placement when product, business, company, project, method, or technical roots compete.

## Completion

The work is complete when every assessed material has one state and primary home, the Seven-directory core and every extension have an explainable responsibility, both maps reference the same authoritative files, planned content is unlinked, technical material remains externally owned, and every applied migration has no stale path or broken link.
