# Structure Tech Docs

Create a company Technical structure that exposes real ownership without mirroring a code repository or pre-creating speculative areas.

## Workflow

1. Read `../../methods/technical-reasoning.md` and `../../methods/documentation-structure.md`. Apply both methods inside this workflow.
2. Classify the request as a `proposal`, `scaffold`, `audit`, or `approved migration`. Require explicit approval before moving, renaming, merging, deleting, or overwriting existing material.
3. Read company navigation, the Technical Assessment when persisted, current Technical Documentation, and representative downstream authority links. Establish the Technical Landscape, logical Stable Responsibilities, and Registered System boundaries from the available evidence. Continue a proposal or audit with explicit assumptions when evidence is incomplete; stop a scaffold or migration that would formalize unsupported ownership.
4. Read `references/technical-structure-model.md` and the writer registries under `../write-technical-doc/references/internal-document-types.yaml` and `../write-technical-architecture/references/internal-document-types.yaml`. Inventory existing and requested material with `assets/technical-inventory-template.md`.
5. Reuse the Documentation Set's language for materialized directories. Admit a Registered System only when its responsibility boundary, owner, and lifecycle are stable; create its System Responsibility README and direct System Architecture entry together.
6. Create a Type Extension only for a justified cross-System responsibility. Create an Event Collection only with its first real event and an existing parent responsibility.
7. Keep Machine Authority and Project Documentation in their owning locations and link them from the narrowest governing Technical document.
8. Read `../../methods/prose-quality.md`, then present or apply `assets/technical-structure-plan-template.md`. Write the truthful Technical root and root-responsibility README and navigation bodies required by the requested structure; route a Registered System's README body to `$Write Tech Doc`. Read `../../methods/visual-production.md` when the request includes a visual or the topology is materially clearer as one. Do not invent strategy, roadmap, standards, systems, or operating facts to populate the tree.
9. Apply an approved migration atomically, updating navigation, links, assets, and named external bindings.
10. Verify language consistency, one primary home per material, real navigation, the Registered System core, no empty extensions or events, and no stale migrated path.

## Boundaries

- Own Technical Documentation topology, materialization, navigation requirements, scaffolding, audits, and approved migrations.
- Use the shared Technical Reasoning Method for scope, authority, ownership, and Type Extension admission.
- Own Technical navigation and root Responsibility READMEs needed to complete the requested structure. Route a System Profile or System Responsibility README body to `$Write Tech Doc`, and route other document bodies to `$Write Tech Doc` or `$Write Tech Arch`.
- Use the shared Documentation Structure Method to resolve placement across Company, Knowledge, and Project documentation.

## Completion

The work is complete when the Technical root exposes its logical Stable Responsibilities in the Documentation Set's language, every Registered System has a System Responsibility README and direct System Architecture entry, every extension and event has its required evidence and parent, Machine and Project authorities remain linked, and any approved migration leaves no broken link or duplicate authority.
