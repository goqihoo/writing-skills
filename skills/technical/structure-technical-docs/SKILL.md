# Structure Tech Docs

Create a company Technical structure that exposes real ownership without mirroring a code repository or pre-creating speculative areas.

## Workflow

1. Read `../../methods/technical-reasoning.md` and `../../methods/documentation-structure.md`. Apply both methods inside this workflow.
2. Classify the request as a `proposal`, `scaffold`, `audit`, or `approved migration`. Require explicit approval before moving, renaming, merging, deleting, or overwriting existing material.
3. Read company navigation, the Technical Assessment when persisted, current Technical Documentation, and representative downstream authority links. Establish the Technical Landscape and responsibility boundaries from the available evidence. Continue a proposal or audit with explicit assumptions when evidence is incomplete; stop a scaffold or migration that would formalize unsupported ownership.
4. Read `references/technical-structure-model.md` and inventory existing and requested material with `assets/technical-inventory-template.md`.
5. Create only the Stable Responsibilities in a default scaffold. Add a Responsibility README to every materialized responsibility.
6. Do not create a Type Extension without independent ownership, governance, or navigation evidence. Do not create an Event Collection before its first real event or without its parent responsibility.
7. Keep detailed system architecture, interfaces, configuration, code, schemas, and runbooks in downstream authority locations.
8. Read `../../methods/prose-quality.md`, then present or apply `assets/technical-structure-plan-template.md`. Write the truthful Responsibility README and navigation bodies required by the requested structure. Read `../../methods/visual-production.md` when the request includes a visual or the topology is materially clearer as one. Do not invent strategy, roadmap, standards, systems, or operating facts to populate the tree.
9. Apply an approved migration atomically, updating navigation, links, assets, and named external bindings.
10. Verify initial-capital directories, one primary home per material, real navigation, no empty extensions or events, and no stale migrated path.

## Boundaries

- Own Technical Documentation topology, materialization, navigation requirements, scaffolding, audits, and approved migrations.
- Use the shared Technical Reasoning Method for scope, authority, ownership, and Type Extension admission.
- Own the Responsibility README and navigation prose needed to complete the requested structure; route other document bodies to `$Write Tech Doc` or `$Write Tech Arch`.
- Use the shared Documentation Structure Method to resolve placement across Company, Knowledge, and Project documentation.

## Completion

The work is complete when the Technical root exposes its four Stable Responsibilities, every extension and event has its required evidence and parent, Responsibility READMEs provide truthful ownership and navigation, downstream authorities remain linked, and any approved migration leaves no broken link or duplicate authority.
