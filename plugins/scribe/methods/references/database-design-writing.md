# Database Design writing contract

Apply this contract when selecting `database-design`, including a database-design section embedded in a broader design. Read the assigned shared asset and apply `../prose-quality.md`; use `../visual-production.md` for applicable diagrams.

## Scope and placement

Treat Database Design as a supporting design with its own data question, not a fifth primary architecture granularity or a new Authority Level. Keep stable database design with its governing System or Subsystem authority; preserve Project authority for a delivery change. Use the same template for reusable reference design while identifying assumptions and applicability instead of inventing a company or delivery commitment.

Choose the scope from the data owners and readers. Place a system-wide database design beside System Architecture in an established documentation set; keep module-private or component-private persistence beside its owning design. Preserve local navigation and language. Create a standalone document when explicitly requested or independently useful for review and maintenance; otherwise embed the relevant content in the owning design. A separate file retains the same authority. Do not infer component ownership merely from use of a database.

Keep system-wide ownership and consistency requirements in System Architecture, functional rules and complete business flows in Module Design, and their database realization here. Link those authorities and explain the local consequence. Use Data Architecture for the broader information-authority, lifecycle and exchange question; select Database Design for entities/tables, constraints, access paths and transactions. Keep database deployment, replication topology, backup facilities and operating procedures with their runtime or implementation owners.

## Develop the design

1. Establish scope, design status, database choice and available sources. Read the relevant schema, migrations and actual access patterns when available. Distinguish implemented definitions from proposed changes; name missing evidence without requiring existing code for a new design.
2. Apply the asset's four-part reader sequence: data model, table design, reads/writes and transactions, then change and validation. Translate the approved Chinese headings for other output languages. Merge these responsibilities into the owning design for embedded work; keep rationale beside each choice.
3. Produce a complete physical field dictionary for every in-scope table using **Physical field dictionary** below. Derive implemented definitions from Machine Authority and identify the source/version; define proposed fields directly when no schema exists. Keep a table inventory separate from the per-field definitions. Preserve executable implementation ownership while supplying the design detail needed to generate its schema.
4. Derive transaction and access decisions from the actual operations. Explain concurrent or duplicate writes only when they threaten a relevant invariant, including the mechanism and observable conflict outcome. Add specific partitioning, archival or migration detail only when supported by the scope; omit unused subsections rather than imposing a generic storage or concurrency checklist. Adapt table terminology to collections or another selected data model when needed.
5. Verify relationships, constraints, access paths and atomic changes together. Check a relevant failure or conflicting operation where correctness depends on it; report proposed checks separately from observed results. End with supported guarantees or explicit design/evidence gaps, not empty placeholders.

## Physical field dictionary

Use a dedicated subsection for each fully qualified physical table name, its Chinese or requested-language name and purpose. List one field per row with this stable schema; translate display labels only for a different output language:

| 字段名 | 数据类型 | 可空 | 默认值 | 主键序号 | 生成方式 | 字段说明 |
| --- | --- | --- | --- | --- | --- | --- |
| `field_name` | `DBMS-native type` | YES / NO | SQL expression / 无 | 1-based position / 无 | DBMS-native generation clause / 无 | Meaning, unit and relevant value interpretation |

Write each actual SQL type completely, including length, precision/scale, array element type or named enum/domain schema when applicable. For types such as PostgreSQL `text` or unconstrained `numeric`, explain the deliberate absence of a length or precision limit rather than inventing one. Expand common/audit fields in every table's physical dictionary; a common-field convention may explain the choice but cannot supply missing rows. Use exact identifiers and separate nullability from default behavior. Use `无` to omit a default or generation clause; use SQL `NULL`, a quoted literal or an expression only when it is the actual declared default. Specify composite primary-key positions explicitly; a field named `id` is not evidence of a primary key. Explain application-generated identifiers beside the table when there is no database generator.

Follow the field dictionary with the applicable named table constraints. Record `UNIQUE`, `FOREIGN KEY` and `CHECK` using exact SQL definitions or equivalently explicit structured entries; include ordered local/target columns, fully qualified referenced table, update/delete actions, matching and deferral behavior where applicable. Keep composite uniqueness as one constraint rather than marking each member individually unique. Specify unique-index null semantics and exact partial-index predicates when they affect correctness. Document extra indexes with their exact name, method, ordered keys/expressions, uniqueness, predicate and included columns; distinguish them from indexes already provided by primary/unique constraints. Retain reasons beside these definitions and keep cross-row business rules with their transaction or application owner.

Resolve types, defaults and constraints from evidence or a visibly proposed baseline when the request authorizes design. Mark a materially unresolved physical definition at its table and identify the blocked generation decision; do not silently guess it or describe the table as ready for schema generation. Replace shorthand such as `field?`, “key fields” or “all target-version foreign keys” with the actual columns. Distinguish external service/user identifiers from local foreign keys. Keep JSON field shape/version obligations explicit without claiming a `jsonb` type validates its business schema.

Before claiming generation readiness, check every table and column name, full type, nullable/default/generation value, primary-key order, constraint/index definition and referenced key. Check field, constraint and index agreement with the existing schema or proposed model. When automated generation is requested, honor the consumer's schema format and provide a source-derived structured export only as needed; a readable Markdown table alone is not a guarantee that an arbitrary generator can consume it. Verify actual parsing or schema construction when claiming that it can, and distinguish empty-schema validation from migrations and business behavior.

## Figures and completion

Include one entity-relationship or equivalent relationship diagram when the design explains multiple related entities. Show identities, relationship cardinalities and relevant ownership boundaries; a single annotated table diagram can satisfy this without three separate conceptual/logical/physical models. For a single entity or unrelated records, explain their structure directly and omit an uninformative relationship figure. Add behavior figures only when an independently explained complex flow warrants one; do not expand every database operation into a second business workflow. Render and inspect applicable figures through the Visual Production Method.

Complete when the reader can identify the data owners, reconstruct the model, locate a complete physical dictionary and explicit constraints/indexes for every in-scope table or a specific unresolved generation gap, connect key reads/writes to access paths and atomic changes, and assess relevant change risks and validation evidence. Verify agreement with the governing architecture, module contracts and available schema, including clearly identified proposals. Confirm conditional topics have a concrete reason to appear and that a supporting document has not duplicated its parent's full architecture workflow.
