# Architecture document families

Apply this method inside architecture Writers. Keep architecture reasoning in `architecture-reasoning.md` and prose quality in `prose-quality.md`.

## Select purpose and document responsibility

Establish whether the request concerns reusable Knowledge, stable Company/System design, or a named Project delivery. Then select the object or topic and its owning template. Keep a view overview, a substantive architecture document, a component, and an engineering strategy distinct. Use navigational overviews for orientation and document maps. Use substantive architectures for design judgments at their scope, including the overall architecture for aggregate cross-view consequences.

Read only the selected template and directly relevant references. Use the Writer's registry for registered type assignments and `architecture-templates/templates.yaml` for shared topic selection. Preserve the output language and explicit user structure. Use the selected template's section sequence and responsibilities as the default output structure, translating headings into the document language. Use its explanatory prompts to develop evidence-grounded, subject-specific content. Treat source documents as evidence for these sections, not as a replacement outline or an additional mandatory view. Separate the analysis used to reach a design from the structure used to explain it. Treat figure slots and comparison or record tables as purposeful aids, adapting their format through `prose-quality.md`. Adapt, merge or omit sections only for an explicit user structure or a concrete scope mismatch; do not reorganize the document merely to mirror the source collection or the reasoning workflow. Remove unfilled placeholders and unused figure slots from the deliverable. Keep selection instructions and acceptance checklists in references rather than adding them to the document body.

## Preserve the reasoning chain

Connect the motivating problem, baseline, constraints and critical scenarios to the organizing strategy before expanding the design. Explain each important boundary or mechanism through the requirement it serves, why the choice fits, its accepted cost and the evidence that could challenge it. Keep rationale beside the affected design; use a decision section for cross-cutting tradeoffs and links. Use an early scenario to establish the required outcome and a later worked flow to demonstrate the design's behavior, rather than repeating the same account.

Scale the chain to the artifact. Let overall architecture own end-to-end choices and allocation; let a subsystem own external commitments and their internal realization; let a component own its contract, invariants and mechanism under allocated constraints. Explain inherited constraints, local choices and matters requiring parent coordination. For Knowledge, teach the reference mechanism with a worked example or change impact and bound it with a failure case or unsuitable context. For delivery, connect actual or proposed choices to the evidence required for acceptance.

## Make the design usable

Apply the responsibility-decomposition rules in `architecture-reasoning.md` before selecting internal nodes. Establish the decision the document must enable. A landscape inventory explains what exists; a reference architecture teaches a reusable model; a concrete architecture supplies a coherent selected or proposed implementation. Treat company/System authority as responsibility, not a reason to omit architecture-significant mechanisms. A company-wide implementation design can specify cross-System realization without copying each System's internals.

For a concrete design, connect logical responsibilities to software modules, runtime units and dependencies. Explain the logical data model through identities, relationships, versions and transaction boundaries. Specify architecturally significant contract operations, input/output meaning, completion and error semantics, synchronous/asynchronous choices and consistency mechanisms. Trace one business result across these choices, including a consequential failure and recovery. State the proposed technology combination and why it fits known constraints. Keep executable schemas, complete API specifications and configuration in their implementation authority; include enough semantic detail here to constrain that work.

Scale this test by level. Overall architecture must let collaborators agree on the system assembly and integration baseline. Subsystem architecture must let component designers implement the allocated guarantees without guessing responsibility or transactions. Component architecture must let implementers identify the algorithm or protocol, state transitions, concurrency assumptions, dependency contracts and observable results. Deployment must realize the units and operating guarantees; migration must preserve the named state through transitions; validation must test those actual mechanisms. Reference knowledge should reach comparable explanatory depth while distinguishing reusable choices, variants and project prerequisites.

When design is requested, develop a recommended baseline from known facts and bounded assumptions. Label new choices as proposals with rationale, alternatives and validation; do not present them as accepted or implemented. For each material unknown, name the affected choice or acceptance boundary and what evidence resolves it. Avoid deferring the entire design because some production parameters or approvals are missing. Preserve established decisions and user scope.

Check whether the intended implementers can identify what to build, how parts interact, what state each owns, what is atomic, how work resumes after failure and how the result is verified. If they still have to invent a cross-boundary mechanism, complete it here or link an existing detailed design that resolves it. A link to an index or an uncreated future document does not resolve a design gap.

## Knowledge and delivery adaptation

Use one shared template family under `architecture-templates/assets/`. Apply the Knowledge Writer's knowledge method for reusable models, variants, applicability and transfer. Apply `architecture-templates/concrete-design.md` for named company, System or Project design. Keep these purpose profiles distinct from structural templates; maintain each architecture skeleton once. Use the delivery method for reference adoption, migration and acceptance responsibilities.

Distinguish design state (current or target), decision state (proposed or accepted), and delivery state (planned or implemented). A delivery request authorizes design work, not invented approvals, external deployment, or claimed acceptance. Keep executable schemas, configuration, code and runbook procedures in Machine Authority; summarize their architecture-significant contracts and link them.

## Document-set boundaries

Support view-based Knowledge organization when the knowledge system uses it. Use Domain, Application, Governance and Runtime as the shared organizing and review framework, following the deferred-category rule in `architecture-reasoning.md`; do not require one document per viewpoint. Preserve other established healthy structures. A view can contain an overview, topic documents and nested object details; document responsibilities and cross-view links govern placement.

Organize delivery around the real object and review/implementation/acceptance tasks. Integrate relevant view content into its main architecture. Split a detailed document only when it has an independent reader task, sufficient substance, and a clear relationship to the main architecture. Avoid creating every available template, one document per view, or every potential component by default.

Maintain each requirement, decision, knowledge-adoption judgment and acceptance result in one owning record. Link inherited decisions; record only local refinements or deviations in child documents. Keep the main architecture responsible for aggregate consequences and the entry document responsible for navigation and status. Connect requirements, design sections, validation scenarios and evidence through descriptive references or explicit links when they span records. Use governed identifiers where they already exist; apply the readable-reference rule in `prose-quality.md` before inventing new labels. Preserve a short standalone explanation without manufacturing a document registry.

## Cross-document scenario check

For a substantive architecture set, choose a critical scenario and a consequential failure at the integrating scope. Trace the intended outcome and invariant through participating modules, information identities and changes, contract completion, control enforcement, runtime behavior and validation evidence. Reuse the same scenario references and meanings across its owning documents; let each document explain its contribution and let the integrating architecture judge whether the combined guarantee holds. Use a concrete change impact for static architecture questions. Keep this proportional to scope; a single-topic request needs only its affected commitments.

Check that parent guarantees are allocated, child mechanisms realize them, and dependency assumptions are provided by an owner. Resolve contradictions in identity, completion, policy, consistency or recovery; identify unsupported assumptions at the guarantee they prevent. A collection of valid links or individually plausible scenarios is insufficient evidence of composition. Complete this check when the selected outcome and failure can be followed across the existing explanations without inventing a missing cross-boundary mechanism.

## Review before completion

Audit each explanatory prompt and figure slot in the selected template against the actual deliverable, not just its heading count. For each applicable figure, verify that the rendered view covers the requested participants, boundaries and relationships. A table or another figure is an adequate substitute only when it communicates that same structure; an internal module diagram does not by itself satisfy an external-context view. Resolve missing applicable views before completion, and explain a deliberate scope-based omission or equivalent substitution in the delivery note. Keep this check in working notes rather than adding a checklist to the artifact.

Check that each decomposition uses justified responsibility boundaries, keeps peer functions separate from shared mechanisms and runtime units, and agrees with the contracts and flow. Compare the completed outline and section content with the selected template; explain any material scope-driven departure in the delivery note. Check that source-derived mappings or analysis have not displaced the architecture model and mechanisms. Verify evidence, current/target distinctions, decision status, and consistency of names, contracts, ownership and views. Confirm the reader can reconstruct the structure and trace important behavior and failure. For Knowledge, verify applicability, variants, transfer and cross-document responsibilities. For delivery, trace requirements through design to observed or planned validation and leave unverified acceptance explicit. Apply the whole-document expression review in `prose-quality.md` to the complete architecture. Check whether responsibility descriptions, product mappings, contract indexes and data-ownership summaries repeat the same boundary facts; consolidate them into their owning explanation while preserving distinct contracts and source links. Verify that the argument remains understandable through its prose and figures, while retained tables have distinct reader tasks. Check that a child realizes its parent commitments rather than repeating the parent explanation. Check actual local links and parent/child navigation when writing into a document set; allow standalone results without invented navigation.
