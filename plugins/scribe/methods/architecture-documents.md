# Architecture document families

Apply this method inside architecture Writers. Keep architecture reasoning in `architecture-reasoning.md` and prose quality in `prose-quality.md`.

## Select purpose and document responsibility

Let purpose determine how content develops, document responsibility determine the template, and the four viewpoints guide design reasoning and completeness checks. Establish Architecture Knowledge or Concrete Design as the purpose; within Concrete Design, preserve stable Company/System authority versus named Project delivery. Identify the object, scope and reader task before selecting a template.

Use the four primary document responsibilities below for object design. Select only independently useful documents; these are optional design granularities, not a required four-level tree. A module may use several components, and a component may serve several modules.

| Document responsibility | Design question | Shared template ID |
| --- | --- | --- |
| Overall Architecture | How do the parts combine to meet the whole object's requirements? | overall-architecture |
| Subsystem Architecture | How does a justified responsibility group internally realize its allocated guarantees? | subsystem-architecture |
| Module Design | How does one cohesive function implement its operations, rules, state changes and processing flow? | module-design |
| Component Architecture | How do the encapsulated mechanisms realize the component's usage contract and required guarantees? | component-architecture |

Keep topic, navigation, decision and delivery-support documents scoped to their own reader tasks. Their existing resources do not extend the primary object-design family or imply a new mandatory template. Use a governing Writer assignment or an explicitly requested existing structure when applicable; otherwise derive their structure from the actual question.

Read only the selected template and directly relevant references. Use the Writer's registry for registered type assignments and `architecture-templates/templates.yaml` for shared topic selection. Preserve the output language and explicit user structure. Use the selected template's chapter sequence and responsibilities as the default output structure. Treat subordinate prompts as explanation obligations; give them separate headings only when they support a distinct reader judgment. Preserve explicitly required user headings. Use its explanatory prompts to develop evidence-grounded, subject-specific content. Treat source documents as evidence for these sections, not as a replacement outline or an additional mandatory view. Separate the analysis used to reach a design from the structure used to explain it. Treat figure slots and comparison or record tables as purposeful aids, adapting their format through `prose-quality.md`. Adapt chapter coverage for an explicit user structure or a concrete scope mismatch. Within each chapter, combine overlapping explanations and organize subsections around the actual design; retain every applicable obligation when changing their boundaries. Remove unfilled placeholders and unused figure slots from the deliverable. Keep selection instructions and acceptance checklists in references rather than adding them to the document body.

Let document responsibility and reader progression determine section boundaries. Use the selected asset's current structure; do not align chapter counts across the four document types. Keep short headings and preserve content obligations when combining sections. Use the primary templates' approved Chinese chapter headings for Chinese output, translating them for another language. Select subordinate titles through the section plan and the Prose Quality Method; a template title alone does not justify a section.

Before planning sections, read the branch contract for the selected template: [overall architecture](references/overall-architecture-writing.md) for `overall-architecture`, [subsystem architecture](references/subsystem-architecture-writing.md) for `subsystem-architecture`, [module design](references/module-design-writing.md) for `module-design`, or [component architecture](references/component-architecture-writing.md) for `component-architecture`. Apply its chapter boundaries, scope adaptation, required views and completion checks across the purposes and authority scopes assigned to that template.

For Database Design, read [database design](references/database-design-writing.md) before planning or embedding the `database-design` template. Apply its supporting-document scope, conditional detail, relationship-view and completion rules instead of expanding it into a full primary architecture document.

## Adapt an explicitly requested stable design

Apply this branch when the user explicitly invokes Write Tech Arch and explicitly requests a stable System Architecture, Subsystem Architecture, Module Design, Component Architecture or Database Design. Retain Write Tech Doc as the default recommendation and registry owner for those artifacts. Use the user's requested result and the target's established authority to preserve its purpose, lifetime and location; selecting a subsystem template alone does not establish Project delivery.

Read the matching entry in `../skills/write-technical-doc/references/internal-document-types.yaml` and its assigned template and `architecture-templates/concrete-design.md`. Read `references/database-design-writing.md` for Database Design, or `../skills/write-technical-doc/references/system-architecture-method.md` for a primary object design. Apply that entry's stable authority and completion profile inside the current invocation. Read these resources directly without invoking another Public Skill, requiring another user invocation, duplicating the registry entry or registering a delivery alias for stable work. Resolve this explicit adaptation before the ordinary Internal Document Type routing stop.

Keep existing design status and distinguish newly proposed mechanisms from established facts. Introduce Project acceptance, cutover or delivery commitments only when an actual Project scope supports them. Preserve the distinction between describing a stable design proposal and approving it as established technical truth. If the object or authority is materially unclear, resolve that uncertainty from sources or ask about that specific missing fact; do not invent a project to fit the Writer.

Complete the adaptation when the selected stable type, governing authority, assigned template and completion profile agree with the requested object, and the artifact has no unsupported Project identity or commitments.

## Plan section questions before drafting

After selecting the template and purpose profile, establish what the intended reader must be able to explain or decide about this object. Turn each applicable section's topic into a reader judgment: what must already be understood to follow it, and what new understanding it provides. Use the branch contract to set its scope. For an implementation or operating explanation, identify the outcome, decision or change the reader must reconstruct through the parts. Plan its supporting sources or proposed choices and material owned elsewhere. Keep this plan compact and internal; use it to order explanatory work within the selected structure, not to generate more headings. For a narrow revision, plan only the affected judgments and inspect their transitions.

Assign each consequential fact or assumption an owning explanation. Retain a local reminder only when it is needed to understand a different mechanism or decision. Use requirements and viewpoint coverage to detect an omitted judgment, then resolve it in the section that owns it. A source requirement that constrains a guarantee must survive expression editing, even when its original heading does not.

Retain a subsection only when its answer has independent substance or the user explicitly requires it. Draft the causal answer before settling its title and boundaries; apply the heading rule in `prose-quality.md`. Merge overlapping answers into their owning explanation and keep a necessary design gap beside the affected guarantee. When repairing a misplaced section, repartition its claims by the questions they answer and reread the resulting argument; moving the whole block or giving it a broader title is not evidence of repair. Distinguish uncertainty about whether a section is useful from missing evidence for a necessary design: omit the former, preserve the latter. Apply the branch contract's content boundaries before grouping remaining material under a generic heading.

For example, let an external-collaboration section establish what callers can request and infer from completion; let internal design allocate those commitments to participants; let data design establish authoritative state and atomic changes; let a worked flow show those participants changing that state; let operation explain behavior under dependency and process failures. Explain a selected choice's rationale beside that choice. Reference an earlier explanation rather than copying its responsibility list into every section.

Map the relevant design elements from **Architecture judgment** in `architecture-reasoning.md` to their owning sections: characteristics and constraints, principles, style, strategies, realizing mechanisms and validation. Preserve their explicit explanation when merging headings. Keep the planning checklist internal, but put the actual design rationale, alternatives and tradeoffs in the artifact. Use descriptive subsections when these choices would otherwise disappear inside a long structure or flow chapter; naming a concept in working notes does not satisfy artifact coverage.

Complete the plan when each retained section has a specific reader question and substantive answer or explicit necessary design gap, consequential facts and assumptions have an owning section, and the reader can move from the design's purpose to its mechanism and verification without a missing step. Preserve the chosen template's relevant responsibilities and adapt it only under the criteria above.

## Preserve the reasoning chain

Establish a compact model early enough to interpret the detailed rules: the object, relevant participants, who initiates or advances the work, what changes and what result they recognize. For a structural question, establish the corresponding relationships and change impact. Choose only what this object needs; do not impose a pipeline or runtime on every design. Explain the object’s defining organization and way of working in the overall solution, including who or what controls consequential choices and what makes an outcome complete where applicable. Let the worked flows demonstrate that model and shared technical topics explain genuinely reused support. Select placement by explanatory role, not by whether the passage mentions a technology or mechanism. Then let later sections deepen how and why the model holds. Keep detailed branches in their owning flows. Explain characteristics, principles, styles and strategies beside the choices they affect, and apply the progression and consolidation rules in `prose-quality.md` rather than repeating the orientation under every heading.

Connect the motivating problem, baseline, constraints and critical scenarios to the organizing strategy before expanding the design. Explain each important boundary or mechanism through the requirement it serves, why the choice fits, its accepted cost and the evidence that could challenge it. Keep rationale beside the affected design; use a decision section for cross-cutting tradeoffs and links. Use an early scenario to establish the required outcome and a later worked flow to demonstrate the design's behavior, rather than repeating the same account.

Scale the chain to the artifact. Let overall architecture own end-to-end choices and allocation; let a subsystem own external commitments and their internal realization; let a module own functional rules, state changes and coordination; let a component own its contract, invariants and mechanism under allocated constraints. Explain inherited constraints, local choices and matters requiring parent coordination. For Knowledge, teach the reference mechanism with a worked example or change impact and bound it with a failure case or unsuitable context. For delivery, connect actual or proposed choices to the evidence required for acceptance.

## Make the design usable

Apply this explanation-and-repair loop while developing each consequential reader judgment, before treating its section as finished. Use it again on the complete reading path after editing. Let the object's purpose and responsibility determine the required depth: an inventory locates existing things, Architecture Knowledge teaches a reusable realization and its applicability, and Concrete Design explains the selected or proposed realization. Apply **Structure-to-flow traceability** in `architecture-reasoning.md` to set the expansion boundary; neither company authority nor a familiar technology name replaces an explanation.

Develop a causal account from the actual design. Connect responsibilities to the implementation and operating choices that matter to the judgment. Explain how an input, interaction or change produces its outcome, why a consequential condition changes that outcome, and which owned mechanism makes the promise hold. Select the necessary decisions, transformations, state/resource effects or handoffs from the object rather than from a universal technical checklist. Keep rationale beside the choice. A simple stateless calculation may need only its rules and intermediate results; a collaboration may require the relationship between contracts, authoritative state and the runtime that executes them.

Test the drafted account from the reader's position. Use only the artifact and specific authoritative explanations it actually links, temporarily setting aside the sources and authoring notes. Reconstruct a representative operation or change through the delivered model, then vary a condition that materially tests its promise. Choose the variation from this object's risks or boundary rules, not a stock failure list. Locate the delivered passage or view that lets the reader determine each consequential step and result. Distinguish understanding what a part is responsible for from understanding how it performs that responsibility. An opaque step is appropriate only at a justified scope boundary with sufficient observable contract semantics; inside the owned mechanism, repeating “process,” “coordinate” or “recover” does not establish the missing decision or transformation.

Compare that reconstruction with the governing evidence and decisions. Find the first point where the reader must invent a condition, mechanism or relationship, or where a different plausible interpretation changes the outcome. Repair that point in its owning explanation and recheck affected prose, figures and linked designs. When the source already establishes the design, supply its missing explanation. When the mechanism itself is unresolved, develop a bounded proposal if design work is authorized; otherwise state the affected guarantee, usable interim boundary and evidence or decision needed to close it. Preserve facts, proposals and implementation status. Unknown operating numbers alone need not prevent a qualitative mechanism from being explained.

Retest the same reader judgment after the repair. Record the tested case, supporting artifact location and material remaining gap briefly in working notes; do not add this test report as a mandatory section. Stop expanding when the reader can reconstruct the owned realization and its consequential boundary without inventing design decisions. Equivalent implementation choices may remain open when they preserve the explained contract. Keep full code, executable schemas, configuration and runbook commands in Machine Authority; include or link the semantic explanation that constrains them. An index or nonexistent future design does not close a missing realization.

Complete this loop when the reader judgment is supported by the delivered explanation at the requested scope. A necessary unresolved design gap may be an honest result of writing or review, but it has not passed that judgment and cannot support an implementation-, operation- or acceptance-readiness claim. Keep that distinction visible at the affected commitment and in the delivery note.

## Knowledge and delivery adaptation

Use one shared template family under `architecture-templates/assets/`. Apply the Knowledge Writer's knowledge method for reusable models, variants, applicability and transfer. Apply `architecture-templates/concrete-design.md` for named company, System or Project design. Keep these purpose profiles distinct from structural templates; maintain each architecture skeleton once. Use the delivery method for reference adoption, migration and acceptance responsibilities.

Distinguish design state (current or target), decision state (proposed or accepted), and delivery state (planned or implemented). A delivery request authorizes design work, not invented approvals, external deployment, or claimed acceptance. Keep executable schemas, configuration, code and runbook procedures in Machine Authority; summarize their architecture-significant contracts and link them.

## Document-set boundaries

Organize Knowledge around the subject, object and reader question. Use the four viewpoints for reasoning and completeness through `architecture-reasoning.md`. Preserve an explicitly requested or established view-based structure when it serves readers; offer viewpoint navigation only as a useful retrieval aid, with links to the owning explanations. Let document responsibilities and dependencies govern placement, without manufacturing four parallel document sets.

Organize delivery around the real object and review/implementation/acceptance tasks. Integrate relevant design concerns into its main architecture. Split a detailed document only when it has an independent reader task, sufficient substance, and a clear relationship to the main architecture. Avoid creating every available template, one document per view, or every potential component by default.

Maintain each requirement, decision, knowledge-adoption judgment and acceptance result in one owning record. Link inherited decisions; record only local refinements or deviations in child documents. Keep the main architecture responsible for aggregate consequences and the entry document responsible for navigation and status. Connect requirements, design sections, validation scenarios and evidence through descriptive references or explicit links when they span records. Use governed identifiers where they already exist; apply the readable-reference rule in `prose-quality.md` before inventing new labels. Preserve a short standalone explanation without manufacturing a document registry.

## Cross-document scenario check

Apply the reader reconstruction in **Make the design usable** at the integrating scope of a substantive document set, and proportionally within a standalone document. Choose materially different commitments that test composition; one successful full run cannot establish an independent entry point or a consequential failure. Reuse the selected scenario or change-impact meanings across the actual owning explanations, including diagrams. Let each document explain its contribution within **Structure-to-flow traceability** in `architecture-reasoning.md`, and let the integrating explanation establish the combined outcome.

Verify that a parent's promise reaches an owned realization and that its dependency assumptions are actually supplied. Resolve contradictions in identity, completion, policy, consistency or recovery in the owning definitions and affected explanations together. Complete when the reader can follow the selected outcome and relevant boundary across the delivered set without inventing a cross-boundary mechanism. A collection of valid links or individually plausible local flows is not composition evidence.

## Review before completion

Complete the ordered reading pass in **Whole-document expression review** in `prose-quality.md`, then reapply **Make the design usable** to the complete artifact. Require both a progressive reading path and a supported reconstruction. Read each title with its parent to predict the question being answered, then compare that prediction with the actual passage and its contribution to the whole. Repair a mismatch in the explanation and its boundaries before renaming it. Collecting answers from distant sections does not repair a missing introduction or transition, and a later technical section cannot supply an absent overall working model. Use the planned reader judgments and selected branch contract to find a missing explanation, not to count headings or keywords. Verify consequential choices through **Architecture judgment** in `architecture-reasoning.md`: their drivers, realization, accepted cost and evidence must remain recoverable from the delivered argument. Apply the cross-document scenario check when the result depends on other designs.

Assess prose and figures separately, then reconcile their names, relationships, conditions and outcomes. Prose must explain the owned mechanism and rationale; each figure must answer its assigned reader question through the visual itself. Neither substitutes for an unsupported answer in the other. Repair a contradiction in both affected expressions through the shared loop rather than surrounding a generic figure with more explanation.

Only then verify the output contract: the selected template's applicable responsibilities and mandatory views, justified scope departures or figure reuse, status and evidence distinctions, Machine Authority boundaries, actual links and real navigation. Mandatory views require actual figures under the branch's reuse/exception rules; optional substitutes must answer the same question. Keep structural checks in working notes and scope departures in the delivery note. When changing a template, map its previous obligations to a new location or justified retirement and test a complete generated artifact; package and outline checks alone do not establish preservation.

Complete writing or review when every consequential reader judgment has either passed the reconstruction or has a bounded, source-grounded unresolved disposition, all reparable expression defects and contradictions have been corrected, and the output contract is met. State which judgments remain unpassed and their effect on readiness. Claim a design ready for its requested use only when those use-critical judgments pass; naming a gap or planning validation does not make the underlying guarantee established.
