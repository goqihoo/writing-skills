# Write Tech Doc

Use one Technical Common Writer for registered and occasional company technical documents without exposing one public skill per document type.

## Workflow

1. Read `../../methods/technical-reasoning.md` and `../../methods/internal-document-types.md`. Apply both methods inside this workflow.
2. Read company and Technical navigation, the Technical Assessment when persisted, the target file, evidence, and representative siblings.
3. Route Project delivery architecture, company-level Technical Architecture, Product-System Map, and a cross-System Architecture Topic to `$Write Tech Arch` and stop before drafting.
4. Establish the named company, Technical Landscape scope, owner, and authority for the remaining Technical artifact from the available evidence. If its authority remains materially disputed, name the evidence or decision required before formalizing unsupported Technical Documentation.
5. Read `references/internal-document-types.yaml`. Select one registered Internal Document Type or classify the requested result as a Freeform Artifact. For Database Design, read `../../methods/references/database-design-writing.md` and apply its complete physical-field contract, including when embedding it in another design. When the result is System Architecture, Subsystem Architecture, Module Design or Component Architecture, also read `../../methods/architecture-reasoning.md` and `references/system-architecture-method.md`.
6. Lock the reader question, Architecture Object and Authority Level when applicable, structure mode, scope, validity, evidence, canonical sources, and excluded downstream detail.
7. Separate observed facts, accepted policy, current technical truth, proposals, decisions, evidence, exceptions, and open questions.
8. Read `../../methods/prose-quality.md` and use only the template assigned by the registry. For architecture artifacts, read `../../methods/architecture-documents.md`, plan section questions, and develop the explanation through **Make the design usable**: test the consequential reader judgment, repair a missing realization or causal link, and retest before treating the affected account as finished. For primary object designs, also apply `../../methods/architecture-templates/concrete-design.md` with the assigned adaptive template. Draft a Freeform Artifact without forcing a template. Apply `../../methods/visual-production.md` when the template requires a visual, the user requests one, or a central relationship is materially clearer as one; apply the branch’s required-view audit before removing a figure slot. Link Machine Authority instead of duplicating executable implementation; retain the complete design dictionary and explicit constraints/indexes required for Database Design.
9. A System Profile writes the Registered System's System Responsibility README. System Architecture, Subsystem Architecture, Module Design and Component Architecture may split supporting documents only when each has an independent reader question, authority, change cadence, and navigation need; update the direct architecture document otherwise.
10. Add or repair real navigation when creating or renaming a document in an existing documentation set. Treat a requested standalone document as complete without a navigation file; keep repository-integration notes outside its reader-facing body. Do not link planned nonexistent files.
11. Apply the complete argument edit and source recheck in the Prose Quality Method; keep working checks separate from reader-facing conclusions. Verify the Internal Document Type, authority boundary, evidence, validity, links, completion profile, and absence of company-level Technical Architecture or Project Documentation responsibilities.

## Boundaries

- Own the Internal Document Types listed in `references/internal-document-types.yaml` and occasional Technical Freeform Artifacts, including System Architecture, Subsystem Architecture, Module Design, Component Architecture and supporting Database Design.
- Let `$Structure Tech Docs` own topology, Technical navigation, root Responsibility READMEs other than a System Profile, and approved migration.
- Let `$Write Tech Arch` own company-level Technical Architecture, Product-System Map, and cross-System Architecture Topics.
- Keep Machine Authority and Project Documentation in their owning locations.

## Completion

For architecture artifacts, apply **Review before completion** in `../../methods/architecture-documents.md` after expression editing. Use its reconstruction result to distinguish completed writing/review from design readiness; a documented gap does not pass the affected reader judgment.

The work is complete when one company Technical scope owns one registered Internal Document Type or Freeform Artifact, any Architecture Object, Scope, and Authority Level are explicit, the applicable completion profile is satisfied, authority and validity are visible, canonical links replace duplicated Machine or Project detail, and real navigation exposes the artifact when the task places it in an existing documentation set.
