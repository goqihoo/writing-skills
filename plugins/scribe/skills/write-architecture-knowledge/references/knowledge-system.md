# Architecture Knowledge systems

## Inventory and plan

For a request to organize or complete a knowledge system, inventory existing entry points, object designs, topics, shared mechanisms and their links before writing. Read representative content, not only filenames. Distinguish an actual file from a README's planned or stale link. Preserve substantive material and healthy local terminology.

Map each file to one reader question, subject, governing parent where applicable, and knowledge responsibility. Identify gaps, duplicate authority and misplaced content. Reuse documents that already answer the question. Apply the primary template responsibilities in `../../../methods/architecture-documents.md` and select the actual asset through `../../../methods/architecture-templates/templates.yaml`. Keep a coverage table in working notes; expose a gap in navigation only as an unlinked gap until its document exists.

Default to subjects, objects and reader questions. Let a knowledge-set entry expose purpose, boundaries, existing documents and useful reading paths. Use overall, subsystem, module or component documents only when each answers an independently useful design question; a reader may enter directly at any needed granularity. Keep cohesive explanations of a problem together even when they involve all four viewpoints.

Preserve a requested or established viewpoint-based structure when it serves readers. Add viewpoint navigation only when it improves retrieval across substantive documents, and link their owning explanations rather than copying them into four parallel accounts. Existing specialist and navigation templates remain resources for explicitly requested or established structures; their presence does not prescribe the knowledge topology.

Assign navigation to entries and indexes and design conclusions to their substantive documents. Let a combined navigation/design document use the substantive template and a short document map, with one location for each conclusion. Keep shared mechanisms in one owning location and link them from dependent modules or topics. Apply the cross-document scenario check in the Architecture Documents Method to establish that the designs compose.

## Materialize within the request

For one document, update only that document and directly affected navigation. For a system-building request, create the agreed or evidence-backed set end to end; do not require separate Public Skill invocations for each artifact. When a topology change is explicitly authorized, migrate with an old-to-new map and repair inbound/outbound links. Preserve unrequested content and avoid destructive replacement; if migration authorization is absent, report the proposed move while completing safe additions or revisions within scope.

Keep existing parent/child placement when it represents ownership. Allow a System to contain modules directly and a component to serve multiple modules; maintain one owning component explanation. Add a topic only for a recurring problem with independently useful substance. Put dependency consequences next to the affected design and link the governing explanation rather than copying it.

Adapt reference examples to the actual subject. Do not copy CEX-specific actors, stages, invariants, or folder names into unrelated knowledge systems. Apply the shared Architecture Reasoning Method before selecting a specialist template; retained templates do not authorize a new category or unsolicited document split. Keep small topics within their parent architecture; create a separate document only for independently useful detail. Treat remaining uncovered responsibilities as explicit extensions instead of silently misclassifying them.

## Completion

Complete a knowledge-system request when the requested scope has a coherent entry, each materialized file has a distinct responsibility and appropriate template, parent/child and dependency links resolve, shared explanations have one owner, and unresolved coverage is explicit without empty placeholder documents. Complete a single-document request when it fits the set and its directly affected links are repaired, or stands alone when requested.
