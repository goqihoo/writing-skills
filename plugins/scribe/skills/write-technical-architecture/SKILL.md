# Write Tech Arch

Produce company Technical Architecture for a Technical Landscape or a coherent Project delivery architecture at the requested scope.

## Workflow

1. Read `../../methods/architecture-reasoning.md`, `../../methods/architecture-documents.md`, and `../../methods/internal-document-types.md`.
2. Establish the requested object, purpose, authority and lifetime from the user's request, target, sources and governing decisions. Select company-level architecture or Project delivery; when the user explicitly requests stable object design through this skill, apply **Adapt an explicitly requested stable design** in the Architecture Documents Method before routing. Preserve the actual scope rather than inferring a Project from a template.
3. For company work, read `../../methods/technical-reasoning.md` and `references/technical-architecture-method.md`; identify the named Technical Landscape and Company Authority Level. For project work, read `references/delivery-architecture-method.md`; establish the delivery object, baseline, requirements and acceptance boundary. For explicit stable adaptation, use the stable resources and completion profile selected by the shared branch.
4. Read `references/internal-document-types.yaml` for company and Project work; use the owning stable registry for explicit stable adaptation. Select the registered type and actual template. For Database Design, read `../../methods/references/database-design-writing.md`, including when embedding it in another design. Treat a compatible cross-System Architecture Topic or occasional Project architectural artifact as a Freeform Artifact. Choose only independently useful supporting documents.
5. Read the selected assets, `../../methods/architecture-templates/concrete-design.md` for shared templates, and `../../methods/prose-quality.md`. Apply **Plan section questions before drafting** in the Architecture Documents Method; preserve explicit user structure and output format.
6. Develop the model at the requested scope through the explanation-and-repair loop in **Make the design usable** in the Architecture Documents Method. Test consequential reader judgments from the drafted explanation, repair the first missing realization or causal link, and retest before treating the affected account as finished.
7. Keep facts, proposals, accepted decisions and implementation state distinct. For Project delivery, record material reference-knowledge adoption and compatibility/migration constraints. For company work, link governing System Architecture instead of copying internal design. For stable adaptation, preserve the governing System/Subsystem authority.
8. Read and apply the complete workflow in `../../methods/visual-production.md` when the selected template requires a visual, the user requests one, or a visual materially improves understanding. Apply it to each figure against its owning section and governing architecture model, through context preparation, type selection, production and semantic completion. Apply the selected template branch’s required-view audit before removing any figure slot. Use a principal view and responsibility explanation for a multi-System architecture. Apply the complete argument edit and source recheck in the Prose Quality Method before final expression review; keep working checks separate from reader-facing conclusions.
9. Update directly affected real navigation for document-set work; allow standalone documents without invented navigation. Verify the selected completion profile, architecture-document reader checks and branch conditions. Remove unfilled placeholders and unused figure slots.

## Boundaries

- Own company-level Technical Architecture, Product-System Map, cross-System Architecture Topics, and Project delivery architecture with its directly required supporting documents.
- Let `$Write Arch Knowledge` own reusable Architecture Knowledge and its document system.
- Let `$Write Tech Doc` own stable System Architecture, Subsystem Architecture, Module Design, Component Architecture and Database Design by default. Honor explicit stable-design requests through the shared adaptation branch without changing registry ownership. Keep Project proposals linked to stable authorities rather than overwriting them.
- Keep implementation tasks, executable schemas, configuration, code and runbook procedures in Machine Authority. For Database Design, produce the complete physical field dictionary and explicit constraints/indexes required by its shared writing contract; identify the source or proposed baseline rather than reducing it to key-field summaries.

## Completion

Apply **Review before completion** in `../../methods/architecture-documents.md` after expression editing. Use its reconstruction result to distinguish a completed writing/review task from a design ready for the requested use; a documented gap does not pass the affected reader judgment.

Complete when the selected company, Project or explicitly adapted stable scope satisfies its owning completion profile and has an intelligible principal structure, consistent ownership and contracts, traceable choices and evidence, and explicit current/target, proposal/acceptance and unresolved-risk distinctions. For multi-file delivery, verify its main entry and supporting artifacts form one coherent reviewable set. Keep unverified acceptance and unsupported commitments explicit.
