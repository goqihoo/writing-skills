# Component architecture writing contract

Apply this reference when `architecture-documents.md` selects `component-architecture`. Use `../architecture-templates/assets/component-architecture-template.md` as the output scaffold. Keep general reasoning, evidence, prose and visual production under their existing Shared Methods; this reference owns Component chapter boundaries, mechanism selection, adaptation and required views.

## Establish the encapsulated responsibility

Explain how an encapsulated mechanism fulfills its consumers' contract and allocated requirements. Identify private or shared use and governing System/Subsystem authority without imposing a module-to-component document hierarchy. Keep one primary design explanation for an object rather than duplicating it because it is called both a module and a component. Select an independent document for an independently useful interface/mechanism explanation, not merely because a class, package or process exists.

Distinguish consumer or business-policy decisions from the mechanism that implements them. Inherit the applicable enclosing style, principles and shared guarantees and explain local consequences; name a separate local style only when it clarifies the actual organization. Preserve stable versus Project scope and reusable Knowledge applicability without inventing deployment, history, approval or delivery commitments.

Follow the four-chapter scaffold and approved Chinese headings, translating them for other output languages. Preserve explicit user structure and narrow-edit scope. Merge short related explanations and omit inapplicable content while retaining important guarantees and implementation depth.

## Select mechanisms from guarantees

Use the component's problem, interface promises, architecture characteristics, constraints and invariants to determine which mechanisms need explanation. Map each consequential promise to its actual realization and later verification. Select named sections for mechanisms whose independent explanation materially helps implementation or review; explain a mechanism once in its owning section.

Treat concurrency as one possible topic, not a compulsory subsection or a proxy for implementation completeness. Precision/rounding, rule precedence/conflicts, encoding/order/compatibility, freshness/invalidation, scheduling/fairness, identity/isolation and other concerns may instead determine correctness. These examples are selection prompts, not a universal checklist. Preserve other material mechanisms supported by the actual subject.

Use state/resource and algorithm/protocol sections only to the extent that they apply. Describe a stateless computation's input, temporary resources and ownership without inventing persistent lifecycle or a communication protocol. State important concurrency or resource assumptions wherever needed, but create a dedicated topic only when there is substantive behavior to explain. Name selected topics directly, such as 精度与舍入 or 并发控制; remove the topic placeholder and do not deliver catch-all headings such as 其他机制. Skip extra topics already explained adequately by the core algorithm, state or structure.

## Keep each chapter's responsibility

1. **组件职责** — Establish the concrete consumer problem and observable result before internal detail. Bound consumers, private/shared use, component versus consumer duties and exclusions. Identify inherited guarantees, priority characteristics, invariant and usage/runtime/resource constraints, and missing budgets. For shared use, distinguish common guarantees from explicit modes or consumer-specific requirements. Explain the actual baseline, behavior to preserve, proposed changes and evidence; merge a brief baseline into scope. Complete when consumers can identify what is promised, their remaining duties and the conditions that make the design applicable.
2. **接口设计** — Explain actual operations and input/output identity, meaning, units/version/context, copy/mutation/retention behavior and returned result/handle ownership. Specify permitted call order, preconditions, completion, lifetime and sync/async/cancellation semantics where relevant; link executable declarations and complete schemas. Explain externally meaningful input rejection, partial failure, timeout/unknown, resource exhaustion and unavailable behavior with effects already incurred, safe retry and residual cleanup duties. Define compatibility/replacement obligations across signatures, meaning, errors, ordering, concurrency, ownership and allocated quality guarantees. Complete when consumers can call safely and decide what to do after success, failure, cancellation or uncertainty.
3. **实现机制** — Start with internal elements, ownership, dependencies and a short working path. Connect important choices to the problem, allocated requirements, applicable principles, alternatives and accepted costs. Establish relevant state/guards, readiness/shutdown, resource acquisition/release, data ownership, persistence, reconstruction and sensitive-data handling before detailed execution where readers need them. Explain an implementable algorithm or protocol when applicable through input assumptions, decisions, intermediate results, output and termination; use a concrete example, formulas or pseudocode as needed while linking full code. Add selected mechanism topics under the criteria above. Explain how failures are detected/contained, what effects may have occurred, what must be retained or released, who retries/recovers and what evidence permits continuation; relate resource/overload/observation assumptions to the consumer and parent runtime. Complete when readers can reconstruct why each important guarantee holds and where its conditions stop holding.
4. **设计验证** — Verify consumer-observable contract and the actual selected mechanisms, not a fixed algorithm/state/concurrency checklist. For each consequential mechanism, identify the supported rule/constraint/characteristic, check conditions and expected observations, boundary/counterexample, method and dependency evidence. Choose computation checks, analysis, walkthroughs, prototypes, tests or observations according to the claim, and state what each can establish. Check compatibility/replacement obligations and, for actual changes, transitions, unfinished work, migration and recovery; otherwise retain only applicable compatibility criteria. Separate planned, partial and completed evidence with version/environment/input/load limits. Distinguish known applicability exclusions from unresolved assumptions, affected guarantees, required evidence/decisions and triggers for another mechanism. Complete when both consumers and implementers can judge supported guarantees, limitations and what must be verified before substitution or wider use.

## Check mechanism realization and ownership

Apply **Review before completion** in `../architecture-documents.md` to the component's prose and rendered views. Make **内部结构与选择** explain the actual or proposed internal elements, what each owns, and the significant calls, data or resource handoffs between them. Use consistent names and explicit relationship meanings; distinguish the component boundary from consumers, runtime carriers and returned results. A model-selection flow or parallel inventory of names does not by itself explain internal composition. Keep a cohesive single implementation simple rather than introducing arbitrary layers.

Trace a concrete call through those elements in the algorithm or protocol explanation. Expose the decisions and intermediate results that establish the guarantee; keep consumer-level orchestration at the boundary. In state/resource and recovery sections, explain only state and resources owned by this component, with a concise reference to consumer duties. For a stateless calculator, explain read-only inputs, temporary resources and failed computation rather than importing the caller's database submission workflow.

When execution can outlive a call or have uncertain effects, make the interface explain how the consumer identifies and queries the original attempt, what cancellation can still prevent, and what evidence permits retry. Distinguish recovering an existing receipt from executing again. Carry the distinction into state guards, recovery diagrams and validation; a generic “check” arrow back to execution is insufficient. Require only operations and lifecycle that the actual mechanism needs.

Keep contract checks, mechanism checks, replacement checks, observed evidence and unresolved design gaps distinguishable even when short sections are merged. Apply the shared scenario trace after a responsibility change, including example calculations, figure labels and verification scope. Complete this check when consumers can act on each meaningful outcome and implementers can explain how the owned mechanism produces it, with explicit limits on unresolved guarantees.

## Required views

Apply `../visual-production.md` internally whenever this template is selected; use its production/render-inspection workflow and the mandatory-view audit in `../architecture-documents.md`. The selected template's requirements take precedence over optional visual-complexity heuristics.

| Location | Requirement | Meaning to show |
| --- | --- | --- |
| 内部结构与选择 | Require an internal-mechanism figure. | Main elements, responsibilities, ownership and dependencies at appropriate detail; do not invent module levels to populate it. |
| Every independently explained key algorithm flow, protocol interaction or other key flow, in any chapter | Require a corresponding flow or sequence figure. | Inputs/actions/decisions/intermediate results or participants/messages/handoffs, including consequential branches and failure/recovery in the main or supplemental figures. |
| 状态与资源管理 | Require a state or lifecycle figure when important state/resource transitions affect correctness, concurrency or recovery. | Relevant states, transitions, guards and acquisition/release/ownership boundaries; stateless computation alone does not require a persistent-state diagram. |

Keep context and verification figures optional unless a key flow is independently expanded there. Give important concurrency or recovery flows their own corresponding figure when independently explained; choose these flows because the actual mechanism needs them, not because they appeared in an example checklist. Formulas, pseudocode, textual steps or a general structure image do not replace a required flow view. Reuse an actual figure only when it explicitly answers the local question. Keep names, conditions and outcomes consistent across contract, mechanism and verification, honor explicit format choices, and explain material scope departures in the delivery note.

## Complete the document

Trace consequential promises from responsibility and interface to the actual mechanisms and evidence. Verify that required behavior remains distinct from replaceable implementation detail and that unsupported business policy, thresholds or verification results were not invented. Check failure/uncertainty and applicability boundaries for the selected mechanisms, required rendered views, and each chapter's completion condition. Finish when each important guarantee has an intelligible realization and appropriate evidence or an explicit gap, without hiding a missing mechanism behind a familiar technical heading.
